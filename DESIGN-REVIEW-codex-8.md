codex
1. **CRITICAL — §§3, 5, 8, 9, 11: the identity bootstrap does not establish safety for the Rust ABI actually used.** `CompilationIdentity` covers the asset layout closure and is compared to the schema, not to the daemon’s compiled module-interface ABI. A long-lived daemon and a newly built pipeline can therefore agree on the asset identity while disagreeing on `Registry`, `ModuleError`, trait-object, or standard-library layouts. Moreover, `AuthoredValue`, `Outputs`, `Result`, strings, vectors, and typed assets cross the dylib boundary by value, contradicting the claim that only serialized artifacts cross; module-allocated values may then be dropped through daemon-side drop glue or a different global allocator. Suggested fix: introduce a separate `ModuleAbiIdentity` covering the daemon/module interface crate, rustc flags, features, standard-library build, and allocator contract, and compare it to an identity embedded in the daemon. Prefer a C-ABI boundary with opaque handles, caller-owned buffers, and module-exported destruction functions.

2. **CRITICAL — §§16–18: `Root.connect(target: Text, protocol)` binds the server’s target but does not verify the client’s target.** If the daemon and game both call a target `macos-dev` but their definitions or bound identities differ, connection succeeds because the client sends neither its expected target-definition hash nor its compiled layout identity. Target-specific blob content can then be silently wrong while logical and layout hashes still match—the exact case §16 says the pack-level target check prevents. Suggested fix: make `connect` carry the client’s expected target-definition hash and compiled identity/layout-table digest, and reject any mismatch before returning `Hub`.

3. **CRITICAL — §§5, 12, 22: `CompilationIdentity` does not cover all inputs capable of changing native layout.** The declared fingerprint covers closure sources, manifests, features, and cfgs, but not build-script outputs, files read by `build.rs`, relevant environment variables, or layout-affecting compiler flags such as layout randomization seeds. For example, a build script can generate a different field order from an external file between source-walk and module compilation while every declared identity field stays equal; the gate passes and a stale native-layout/fixup identity can cause miswrites or UB. Suggested fix: hash the effective compiler invocation and generated source inputs/outputs, including build-script rerun inputs and layout-affecting rustflags, or embed and compare a compiler-produced per-type native-layout table digest.

4. **CRITICAL — §§12, 15: the normative `FixupPlan` cannot express the typed construction and cleanup contract its prose requires.** `ConstructMap` contains no typed constructor/inserter or hasher identifier, although `HashMap` has a private representation and construction depends on its `BuildHasher`; `ConstructArc` has the same problem with private allocation metadata. The promised rollback stack needs typed drop functions, but no operation or plan table carries them. `NativeTagWrite` also lacks an explicit payload-derived niche case for variants whose payload establishes the native tag. Implementing these operations from offsets alone is unsound; relying on an undeclared global table leaves its identity and unload lifetime unkeyed. Suggested fix: add generated, consuming-binary-owned constructor/insert/drop helper tables, reference them explicitly from operations, key them by native identity, and model payload-derived niche encodings and operation order directly.

5. **HIGH — §§5, 12: the strengthened DSWL recursion is not finite for recursive asset types.** Logical schemas explicitly support recursion, but DSWL now embeds the pointee node under every `Vec`, `Box`, and `Arc` without defining a back-reference. `struct Node { children: Vec<Node> }` therefore expands forever. The tree-shaped `sub_plans: Vec<FixupPlan>` likewise does not define how a `PlanId` can refer to an ancestor or itself. Suggested fix: add versioned DSWL node IDs/back-references and define fixup plans as a finite arena graph whose `PlanId`s may form guarded cycles through indirections.

6. **HIGH — §§3, 6, 11: `DefaultTable<T>` cannot support the declared adoption and migration semantics.** Its field table is keyed only by direct field name, while migration operations target arbitrary `FieldPath`s. Adding a defaultable field inside a nested non-`AssetType` struct, or adopting a sparse nested object, has no representable writer despite a valid `Default` implementation. Separately, a procedural macro cannot generally determine at expansion time whether arbitrary field types or `T` implement `Default`. Suggested fix: generate tables over the complete serializable type closure, keyed by schema node/path and default source, and use explicit/default-provider annotations or compiler-checked registration rather than claimed proc-macro trait discovery.

7. **HIGH — §§3, 9: per-epoch tool staging conflicts with trace revalidation.** After tool v1 is staged on first use, replacing the registered executable with v2 makes the stored trace fail revalidation, but a new execution in the same module epoch still runs the frozen v1 copy. The system can either repeatedly miss and rebuild with v1 or publish a newly completed result using code no longer present at the registered path. Suggested fix: stage a fresh stable snapshot whenever the observed tool content changes, store staged copies by content hash, and execute the copy selected for that invocation; alternatively, make tool changes rotate the entire `PipelineEpoch`.

8. **HIGH — §§3, 11, 13, 17: `LoadContext` binds its code fields together but does not bind its snapshot to that epoch.** A snapshot capability can outlive a pipeline reload, while old modules are drained and unloaded. A later resolve on that snapshot can therefore be paired with the new epoch even though its terminal-type/tag indexes were produced under the old map, or it becomes impossible to execute because the required old module is gone. `InputVersion` is also declared as watcher/authoring-driven without an explicit code-epoch component. Suggested fix: record the pipeline epoch/dylib identity in every snapshot basis, publish epoch changes as input-version events, construct `(MetadataSnapshot, PipelineEpoch)` atomically, and return `Drifted(Dylib)` when an old snapshot can no longer use its original epoch.

9. **HIGH — §§14, 17: the per-file content-hash recheck is still a check-then-replace race.** An external editor can save after the operation rehashes a file but before its atomic rename; the daemon then overwrites the newer edit despite the “never overwriting a concurrent edit” guarantee. The base-version check has the same problem for filesystem changes not yet consumed by the watcher. Suggested fix: require a real compare-and-swap publication mechanism based on an inode/version token where supported, or a cooperative workspace write lock. Where unconditional atomic replacement is unavoidable, preserve the displaced file as a conflict artifact rather than claiming overwrite prevention.

10. **MEDIUM — §§3, 5, 9, 16, 18: the canonical encodings behind foundational identities are not normative.** The C bootstrap refers to a “canonical `CompilationIdentity` encoding,” and target hashes use a “canonical `Target` encoding,” but neither grammar is defined. `Target.apis` is semantically a set yet remains an unsorted, non-deduplicated `Vec`. Different component versions can therefore disagree on string lengths, enum encodings, or API ordering, causing incompatible target hashes and pack rejection. Suggested fix: specify versioned, domain-separated byte grammars for both records and canonicalize every set before hashing.

11. **HIGH — §§9, 13: the CAS framing has bounded key fields but the registration API has no corresponding bounds.** Segment records use `u16` for `key_len` and `out_key_len`, while processor IDs, output keys, output counts, and serialized action keys are unbounded. A valid registration can exceed 65,535 bytes; truncation creates cache aliases, while rejection makes an otherwise accepted API input unreachable. Suggested fix: enforce checked length/count caps during registration and define them in the traits, or widen the record fields and still reject overflow explicitly.

12. **MEDIUM — §§5, 22: `manifest_lock_hash` is not scoped consistently with the layout closure.** It is described as covering cargo manifests plus the entire `Cargo.lock`, so changing a pipeline-only tool dependency changes the identity and rejects the module until schemas are regenerated, even though pipeline-only dependencies are deliberately outside layout identity. Suggested fix: hash the manifests and resolved lockfile nodes belonging to the layout closure; put daemon/module-interface and pipeline-code concerns in their separate ABI and dylib identities.

13. **MEDIUM — §§8, 17, 18: new imports cannot select a destination root.** `ImportRequest.dest` is only a merged-namespace root-relative path. When multiple asset roots are configured and the destination does not yet exist, there is no mapping to a physical root and no ambiguity rule can choose one. Suggested fix: add a stable asset-root identifier to import/create requests, while retaining merged root-relative paths for reads and queries.

14. **MEDIUM — §§6, 8, 17: settings semantics are contradictory for `import` into an existing destination.** The fold says the prior settings entry survives, while `ImportRequest.settings` is mandatory and §17 says an existing destination makes the request a re-import fold. Thus the supplied value is either silently ignored or overwrites prior settings contrary to the fold invariant. Suggested fix: reject a differing `settings` value for an existing bundle, define it explicitly as an update, or separate “update settings and import” from `reimport`, which should consume only the recorded entry.
