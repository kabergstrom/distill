1. **CRITICAL — §§5, 12, 22 — DSWL can treat semantically different wire layouts as identical, causing silently swapped fields or invalid enums.**  
   The document says declaration reordering is harmless logically because “layout cares; the layout hash covers it” ([DESIGN.md:322](/Users/karl/Projects/distill/DESIGN.md:322)). But DSWL contains field nodes without field names and enum nodes without native discriminant mappings: “`kind … wire_offset … wire_size … wire_align`” with variants merely “in name-sorted order” ([DESIGN.md:1488](/Users/karl/Projects/distill/DESIGN.md:1488)). For `struct S { a: u32, b: u32 }`, reordering the two fields can leave the DSWL sequence as two indistinguishable `u32` nodes at offsets 0 and 4, while changing which name occupies each offset. Bundle bytes, logical hash, and layout hash can all remain unchanged, so the old artifact is reused and flat-copied into the new layout with `a` and `b` swapped. Enums have the same problem: the fully-flat form preserves native tag bytes, but DSWL does not hash tag offset, actual discriminant values, or name-to-native-variant mapping. `SwitchVariant` likewise has only `variants: Vec<PlanId>` and no instruction capable of writing each variant’s native direct/niche encoding ([DESIGN.md:1456](/Users/karl/Projects/distill/DESIGN.md:1456)). The codebase confirms the current limitation: `TagEncoding::Direct` contains only `tag_size` ([ngp-schema/src/lib.rs:102](/Users/karl/Projects/newgameplus/ngp-schema/src/lib.rs:102)), source-walk emits only that size ([source-walk/src/main.rs:2265](/Users/karl/Projects/newgameplus/source-walk/src/main.rs:2265)), and ngp-reflect currently assumes a base-offset tag whose numeric value indexes the variant vector ([ngp-reflect/src/traverse.rs:167](/Users/karl/Projects/newgameplus/ngp-reflect/src/traverse.rs:167)).  
   **Fix:** hash semantic field identity with every wire offset and full per-variant wire encoding. Add native tag offset/value/niche metadata and explicit per-variant native-write instructions. Prefer separate `WireEncodingHash` and `NativeFixupHash`, with fixup plans keyed by both; otherwise include the complete native↔wire mapping in `LayoutHash`.

2. **HIGH — §§3, 5, 12, 18, 22 — the three-way `CompilationIdentity` gate makes cross-target cooking impossible even after the sole open item lands.**  
   The pipeline cdylib exports one host identity via `identity() -> CompilationIdentity` ([DESIGN.md:138](/Users/karl/Projects/distill/DESIGN.md:138)), while a cross-target layout table is bound to the target identity ([DESIGN.md:2150](/Users/karl/Projects/distill/DESIGN.md:2150)). A macOS daemon must load a macOS cdylib; that module cannot truthfully attest a Windows target triple. Requiring schema/layout identity, target binding, and module attestation to “all agree” ([DESIGN.md:2392](/Users/karl/Projects/distill/DESIGN.md:2392)) therefore still rejects Windows cooking after Windows layout emission exists. The claim that per-target layout emission is the “one open item” gating a second platform is false as written.  
   **Fix:** split this into a host `ModuleAbiIdentity` compared between daemon and loaded cdylib, and a per-target `LayoutCompilationIdentity` compared between target binding and layout table. Use a target-independent asset-schema/source fingerprint to prove the module and layouts describe the same types. Package-qualify feature/cfg sets as well; a workspace-wide unqualified `BTreeSet<String>` can alias identically named features from different crates.

3. **HIGH — §§9, 13, 22 — the derived-output row stores an unstable stage in a target- and basis-independent index.**  
   Extra UUIDs are explicitly stable “even when an output moves between stages” ([DESIGN.md:784](/Users/karl/Projects/distill/DESIGN.md:784)), and chains may differ per target ([DESIGN.md:850](/Users/karl/Projects/distill/DESIGN.md:850)). Yet resolution uses `child uuid → (parent uuid, stage, output_key)` ([DESIGN.md:979](/Users/karl/Projects/distill/DESIGN.md:979)), with no target hash, pipeline-map identity, or input basis. That conflicts with §13’s claim that memo state is monotone and basis-keyed. A module reload or a second target can assign a different producing stage to the same child UUID, overwriting or ambiguating the global row. The body and storage table also disagree on whether `stage` is present ([DESIGN.md:1531](/Users/karl/Projects/distill/DESIGN.md:1531)).  
   **Fix:** make the only global mapping the immutable `child → (parent, output_key)`. At resolution, use the snapshot’s pipeline map and connection target to locate the producing stage. Alternatively key the stage-bearing row by child, target-definition hash, and pipeline-map/input basis.

4. **HIGH — §§10–11, 13 — `load_current` cannot reach the inputs its semantics require.**  
   The function must query normal `Migration` assets at every visited node, record positive and negative `migration_edge` query dependencies, execute registered migration functions/default materializers, and bind all of that to a pinned snapshot. Its declaration receives only `entry`, `bundle`, and `&SchemaRegistry` ([DESIGN.md:1287](/Users/karl/Projects/distill/DESIGN.md:1287)). It has no metadata snapshot/query interface, migration-function/default registry, module epoch, or authoritative dylib hash. Consulting live global state would violate snapshot consistency and could return a plan different from the `LoadInputs` it records. `SchemaRegistry` itself is not declared despite §22’s “every structure and API” claim.  
   **Fix:** declare an explicit `LoadContext` containing the pinned metadata snapshot/query service, schema archive/current registry, migration/default function registry, module epoch/hash, and planner version, and pass it to `load_current`.

5. **HIGH — §§3–4, 6, 11–12 — the declared default registry cannot implement field defaults or skipped-field construction.**  
   `Registry::defaults<T>` requires `T: AssetType + Default` ([DESIGN.md:148](/Users/karl/Projects/distill/DESIGN.md:148)), but `WriteFieldDefault` requires `Default` for arbitrary nested field types, not asset roots ([DESIGN.md:1207](/Users/karl/Projects/distill/DESIGN.md:1207)). More seriously, `WriteSkipDefault { default_of: TypeUuid }` ([DESIGN.md:1455](/Users/karl/Projects/distill/DESIGN.md:1455)) cannot describe the document’s own skipped `Option<GpuMeshHandle>` field: it has no asset `TypeUuid`, and skipped fields are absent from the logical schema. The fixup executor therefore lacks both a callable default writer and a valid key for it. Failure to initialize such a field before treating the enclosing object as a Rust value is memory-unsafe.  
   **Fix:** generate/register default-write functions for every required native field type, keyed by a compilation-scoped native type identifier rather than asset `TypeUuid`; retain skipped-field type/default metadata in the layout schema. Another safe design is to materialize the whole asset’s `Default`, overwrite serialized fields transactionally, and preserve correct drop ownership.

6. **HIGH — §§12, 15–16, 22 — composite CKey verification omits blob-section padding.**  
   Raw CKeys hash the complete artifact, whose blobs are individually 16-byte aligned ([DESIGN.md:1357](/Users/karl/Projects/distill/DESIGN.md:1357)). The fetched/packed composite is instead defined as “structural buffer ‖ extents in blob-table order” ([DESIGN.md:1377](/Users/karl/Projects/distill/DESIGN.md:1377)), and `FetchedArtifact` carries only structural bytes plus one `Blob` per entry ([DESIGN.md:1926](/Users/karl/Projects/distill/DESIGN.md:1926)). If a blob length is not a multiple of 16, the raw file contains zero gaps before subsequent blobs, but those bytes belong to neither the structural buffer nor any payload extent. Hashing the declared composite cannot reproduce the raw CKey. This contradicts §22’s claim that composite verification is resolved.  
   **Fix:** normatively hash zero padding synthesized from blob-table offsets between extents, or include padding segments in the fetched encoding. Define precisely whether the pre-blob alignment pad belongs to `structural`, and reject nonzero or noncanonical gaps.

7. **HIGH — §§6, 8, 10, 22 — watched-import provenance has no declared on-disk carrier.**  
   The settings asset must carry source path(s), importer identity, `watch`, and the complete recorded read-set so re-import survives loss of `.distill/` ([DESIGN.md:535](/Users/karl/Projects/distill/DESIGN.md:535)). But `Importer::Settings` is an unconstrained `AssetType`; no trait or wrapper requires any of those fields ([DESIGN.md:614](/Users/karl/Projects/distill/DESIGN.md:614)). `ImportOutput` says the daemon writes the settings entry and read-set but exposes no representation for them ([DESIGN.md:639](/Users/karl/Projects/distill/DESIGN.md:639)). There is also no declared raw-file dependency value type covering content hash, probe result, and `FileQuery` result, nor a stable persisted importer ID. After daemon-state deletion, the daemon cannot generically reconstruct which importer to run or which raw-file observations to validate.  
   **Fix:** declare a built-in import envelope, for example `ImportRecord { importer_id, sources, watch, read_set, settings_type, settings }`, with a normative `FileDep` enum for read/probe/enumerate observations. Keep raw paths domain-distinct from `AssetRef`/`WeakAssetRef`.

8. **HIGH — §§3, 22 — the module ABI contradicts both Rust FFI safety and the promised panic containment.**  
   `extern "C" fn() -> CompilationIdentity` returns `String` and `BTreeSet` across a C ABI, while `extern "C" fn(&mut Registry)` passes a non-`repr(C)` Rust service object ([DESIGN.md:134](/Users/karl/Projects/distill/DESIGN.md:134)). These are not FFI-safe declarations. In addition, a panic escaping an `extern "C"` function does not become an ordinary unwind caught by a host-side `catch_unwind`; it aborts at the non-unwind ABI boundary, contradicting “a panic in pipeline code fails that job, not the daemon” ([DESIGN.md:120](/Users/karl/Projects/distill/DESIGN.md:120)). This is separate from the accepted same-rustc risk. The cited newgameplus host uses Rust-ABI `unsafe fn` for same-toolchain callbacks ([module_state.rs:31](/Users/karl/Projects/newgameplus/newgameplus/src/module_state.rs:31)) and pointer/length symbols when moving strings across the library boundary ([module_state.rs:1034](/Users/karl/Projects/newgameplus/newgameplus/src/module_state.rs:1034)).  
   **Fix:** either formally use unsafe Rust ABI throughout under the same-rustc contract, or expose a POD callback table plus byte buffers. Catch panics inside each exported module wrapper and return an error status. Deep-copy every registered ID/key into daemon-owned memory and explicitly drop all module-vtable-bearing objects before `dlclose`.

9. **MEDIUM — §§3, 9 — no registration API can create the specified per-target pipeline maps.**  
   The design permits one processor per `(input type, target)` and chains that “may differ per target” ([DESIGN.md:850](/Users/karl/Projects/distill/DESIGN.md:850)), but registration is only `Registry::processor(p)` ([DESIGN.md:143](/Users/karl/Projects/distill/DESIGN.md:143)). Neither `Processor` nor `OutputDecls` declares a target selector. The registry therefore cannot determine which targets a processor participates in, detect per-target duplicates, or validate per-target chains.  
   **Fix:** add a target predicate/key to registration or a static `Processor::targets() -> TargetSelector`; include that selector’s canonical form in pipeline-map identity.

10. **MEDIUM — §§15, 22 — `StaleLastGood` state semantics still contradict the merged-component rollback rule.**  
    The body says `StaleLastGood` freezes an entire component and later says every lagging component member is in `StaleLastGood` ([DESIGN.md:1730](/Users/karl/Projects/distill/DESIGN.md:1730), [DESIGN.md:1873](/Users/karl/Projects/distill/DESIGN.md:1873)). The round-5 rule instead says “only assets whose own resolves actually failed are labeled `StaleLastGood`” ([DESIGN.md:1831](/Users/karl/Projects/distill/DESIGN.md:1831)); §22 repeats both positions ([DESIGN.md:2376](/Users/karl/Projects/distill/DESIGN.md:2376), [DESIGN.md:2411](/Users/karl/Projects/distill/DESIGN.md:2411)). Successful-but-not-adopted members of a failed pre-existing component therefore have no specified state: `Current` is false for latest inputs, while labeling them stale violates the “only actually failed” rule.  
    **Fix:** keep actual failures in `StaleLastGood`; keep blocked successful members in `Invalidated`, or add `BlockedBy { failed: AssetUuid }`. Define component freeze as loader graph state rather than implying every entry shares the failure state.

11. **MEDIUM — §17 — the normative import RPC violates the stated write-precondition rule.**  
    The prose says “All writes … carry the base store version as a precondition” ([DESIGN.md:2080](/Users/karl/Projects/distill/DESIGN.md:2080)), but `Hub.import(path, settings)` has no base version ([DESIGN.md:2063](/Users/karl/Projects/distill/DESIGN.md:2063)). An import is an authoring write and folds over a prior bundle, so concurrent edits can materially change the identity/settings basis it should preserve.  
    **Fix:** add `base: UInt64` and enough identity to name the intended prior/output bundle, rejecting a mismatch before running the fold; alternatively explicitly specify serialized “always fold latest” semantics and remove the universal precondition claim.
