1. **CRITICAL — §8, §10: `FileQuery` result hashing has exact structural collisions.**  
   The normative formula is `blake3("FILQ" ‖ sorted paths)` without a count or per-path length. Results `["a", "bc"]` and `["ab", "c"]` both hash the bytes `"FILQabc"`. A watched glob can transition between those sets without invalidating, leaving imported bundles and downstream artifacts silently stale. Fix by hashing a versioned encoding containing the result count and length-prefixed normalized paths.

2. **CRITICAL — §3, §5: `ModuleAbiIdentity` does not identify the actual host-interface ABI.**  
   `interface_fingerprint` covers only interface-crate sources. It omits the daemon-side enabled features/cfgs, transitive dependency identities, build-script outputs, ABI-relevant compiler flags, and other inputs that can alter `Registry`, `Outputs`, `ModuleError`, or their nested types. For example, daemon and module can compile the same sources with different interface features, report identical `ModuleAbiIdentity`, and then pass differently laid-out Rust values by reference/value—causing UB. The free-form allocator string also does not prove that separately linked allocator instances support cross-module allocation/free. Fix by hashing the complete resolved interface ABI closure independently for daemon and module, including features/cfgs/build outputs/dependency versions, and either mandate a precisely defined cross-module allocator/linkage contract or keep allocation and destruction on the originating side through opaque handles and explicit callbacks.

3. **CRITICAL — §3, §5, §12: the module’s measured-layout check is unreachable through the normative API.**  
   `PipelineModuleTable::identity` returns only `CompilationIdentity` and `ModuleAbiIdentity`; `Registry` has no layout-attestation method. Thus the daemon has no declared way to obtain exhaustive per-type module measurements and compare them with source-walk before accepting typed processor/default/validator registrations. An untracked build-script or cfg change can therefore alter a module type’s offsets while declared identities still match, after which daemon-side encoding or traversal of a module-owned value can silently swap fields or touch invalid pointer slots. Add a length-framed, C-ABI layout-attestation export—preferably a sorted table of `(TypeUuid, native-layout digest/details)`—and reject missing, extra, or divergent types before any asset value is exchanged.

4. **HIGH — §14: swap-back publication still has a second race that can lose a newer user edit.**  
   Suppose the expected preimage is `A`, the user has already installed `B`, and the daemon exchanges in `D`. It detects displaced `B` as a conflict. Before the exchange-back, the editor atomically installs newer `C` over `D`. The specified exchange-back then makes `B` the target and displaces `C` into the temporary path, which the normal cleanup can discard; the newest user bytes lose despite the stated guarantee. Before rollback, verify that the target is still the exact daemon inode/content, and after every exchange verify the newly displaced object. Any unverified version must be preserved under a named conflict path; retry or stop rather than deleting it.

5. **HIGH — §5, §16, §18: the pack header cannot perform its promised measured-layout mount check.**  
   The normative pack header carries `Target` and `target-definition hash`, while that hash binds only `Target` plus `CompilationIdentity`; `CompilationIdentity` contains no measured native-layout digest. Unlike `Root.connect`, the pack path has no separate layout-identity field. A pack and game affected differently by an undeclared build input can therefore share the target hash, and the claimed mount-time rejection cannot be implemented. Store the expected measured native-layout identity explicitly in the pack manifest header, bind it into the pack identity, and compare it with the game’s generated measurement before exposing any artifact.

6. **MEDIUM — §3, §11, §12: panic containment does not cover all callbacks crossing the module boundary.**  
   Importer, processor, and validator calls occur through registered trait objects, while `DefaultTable` exposes plain infallible `fn() -> AuthoredValue` pointers. Constructor, skip-default, and drop callbacks likewise need an explicit no-unwind contract. A user `Default` panic cannot be represented by the declared signature and may unwind across the dylib boundary; a rollback drop panic can abort during an existing failure. Generate module-side catching thunks for every callback and make callback tables return fallible status/results. Define destructor failure as leak-and-report or otherwise guarantee that generated drop thunks cannot unwind.

7. **MEDIUM — §3, §11: `DefaultTable`’s dotted-string keys do not uniquely address the full schema tree.**  
   A path such as `mode.x` cannot distinguish `mode.A.x` from `mode.B.x` in an enum, and transparent traversal through `Vec`, `Option`, map keys/values, or nested parents has no normative segment grammar. Consequently two default writers can collide or a `WriteParentDefault` can select the wrong parent node. Replace strings with a canonical structural path containing field, variant, element, map-key, and map-value segments, or specify an injective escaped binary encoding for those segments.

8. **MEDIUM — §7, §9, §13, §17: derived UUIDs can become unresolvable after eviction or daemon-state loss.**  
   The child-to-parent mapping is rebuilt only from committed result records and evicts with those results. After lease expiry, restart, or deletion of `.distill`, a reconnecting client may hold only an extra-output UUID learned earlier. `resolve(child)` cannot invert UUIDv5 and therefore cannot discover which parent to rebuild, contradicting the promise that reconnecting clients can re-pull and daemon state is reconstructible. Because output declarations are static, build a metadata-only reverse index from every authored parent UUID and every applicable chain output key at epoch publication; this does not violate laziness because it creates no artifacts.

9. **MEDIUM — §8, §17, §18: `ImportRequest.root` names an identifier the configuration does not declare.**  
   The RPC says `root` is an asset-root ID, but `[assets].directories` is only a list of paths. There is no stable ID-to-directory mapping, so a new destination cannot normatively select its physical root. Raw-source and `FileDep` paths also contain no root identity, making an ambiguous same-relative-path source impossible to select or persist for reimport. Define asset roots as named entries and carry the root ID in destination selection and, where physical selection is allowed, source/read-set path identities.
