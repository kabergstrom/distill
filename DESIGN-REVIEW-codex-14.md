codex
1. **CRITICAL — §5, §8, §12:** The DSWL indirection-node grammar omits set element schemas. It specifies child nodes for vectors, boxes, arcs, and maps, but not `HashSet`/`BTreeSet`; the earlier `VarRef.len` definition likewise mentions only `Vec` and `HashMap`. Consider an authored `BTreeSet<Elem>` where `Elem`’s fields are reordered. The logical hash and canonical bundle bytes remain unchanged, but the element wire order changes. Because the set node does not hash its element node, the layout hash and DSBI key can remain unchanged, serving the old artifact. The new fixup plan then interprets old element bytes using the new layout, silently swapping fields or constructing invalid values. Add set element nodes to DSWL exactly like vector elements, define `VarRef.len` as the element count for both set kinds, and test nested relayouts under every indirection kind.

2. **MEDIUM — §5, §11:** Sets have no migration operation. `MigrateElements` normatively covers only `Vec`/array/`Option`/map values, while `MigrateMapKeys` handles the key-like collision semantics separately. A migration such as `Set<u8> → Set<u16>`, or a custom element transformation that merges two formerly distinct elements, has no specified executor path or duplicate-integrity check. Add `MigrateSetElements`, or explicitly extend `MigrateElements` to reconstruct sets through their real equality/ordering semantics and fail on duplicate results.

3. **MEDIUM — §5, §11, §19:** The shared migration planner cannot receive the identity data its prose requires. Both the embedded historical input and `SchemaRegistry::current` expose only `LogicalSchema`/`SchemaNode`, deliberately stripped of `TypeDef`, `TypePath`, `SchemaTypeId`, and nested type UUIDs. Yet plan computation says type matching uses `TypeDef` UUIDs with crate-and-name fallback. Only the root entry’s `type_uuid` remains available; nested matching inputs are unreachable. Define the disk planner as an AST-to-AST structural/path planner, reserving nominal `TypeDef` matching for engine hot reload, or add a hashed migration projection carrying every identity the shared planner actually needs.

4. **MEDIUM — §5, §19:** The normative schema split does not declare the refactored `Field`, `TypeAttrs`, or field-attribute records. This is material because the current engine `Field` contains `offset`, `field_size`, and `FieldShape`. Retaining it means `Schema.types` is not logical-only; removing those members leaves no normative declaration for field identifiers, type references, `skip`/`blob`/`tag`/`rev`, or correspondence with `FieldLayout`. Fully declare the logical `Field` and attribute structures, and state the exact positional/ID relationship between every field and its per-identity layout row.

5. **MEDIUM — §12:** `CtorEntry::push` cannot report the duplicate-element/key integrity errors promised for `ConstructSet` and `ConstructMap`; it returns only `Result<(), CallbackPanic>`. A real set insertion returns an inserted/not-inserted result, while a map insertion may replace an existing value. Ignoring that result silently changes verified data; mapping it to `CallbackPanic` conflates malformed artifacts with callback failure. Give `push` an explicit error/disposition such as `Duplicate | CallbackPanic`, and specify how map key/value temporary ownership is passed through its single `elem` pointer.

6. **MEDIUM — §8, §9, §13:** The DSBI lookup key has no compatible durable result-record representation. Section 8 says the `"DSBI"` digest is the fully static build-import lookup key, but §9’s orientation table says there are only two lookup keys, and §13 requires every committed result record to carry a `"DSSI"` digest plus the canonical `StaticInputs` payload. `StaticInputs` cannot represent bundle bytes, reference-resolution results, or migration inputs. Consequently an import payload either lacks a valid commit marker and becomes garbage on recovery, or must be shoehorned into a processor-key format contrary to the normative grammar. Define a separate `BuildImportInputs`/DSBI result variant and index, or generalize result records into explicitly tagged DSBI and DSSI key forms.

7. **LOW — §9, §15, §16:** The global rename left misleading cache terminology. Section 9 says “the input hash … is the index” immediately after defining the full input hash as never stored; §15 still says “the cache key cannot be computed client-side”; and §16 calls `ContentHash` “the same identity the build cache uses,” although cache lookup uses the static-input-key digest. Name the static-input key as the lookup index, describe the full input hash only as a witnessed determinant, and reserve `ContentHash` for CAS/fetch identity.
